# 行内 Trace Server 接入就绪评估与准备清单

核查日期：2026-10-10  
核查对象：AgentGate 当前工作区中的行内执行、Trace 查询与证据校验实现。  
用途：判断能否进入行内联调，明确准备事项、责任分工和验收标准。

## 1. 当前结论

**工程已具备行内 Trace Server 的接入和取证能力，可以进入联调；真实行内环境能否直接使用，尚未验证，不能仅凭配置 URL 判断。**

| 判断层次 | 当前状态 | 说明 |
|---|---|---|
| 工程查询与取证能力 | 已具备 | 支持按每轮 Trace 引用查询、校验、转换为测评证据 |
| 本地接口契约验证 | 已通过本次相关回归 | 111 项通过，12 项因协议不适用跳过 |
| 真实行内网络、鉴权和数据兼容性 | 待联调 | 本次未连接真实行内服务，未核验实际部署配置与凭据 |
| 真实行内端到端验收 | 待完成 | 需用真实智能体验证上报、关联、查询、展示及失败处理 |

当前测试使用模拟行内网关和独立的本地 HTTP Trace 服务。本地通过不等于真实行内平台已经通过验收。

## 2. 接入链路与已有能力

```text
被测智能体 ──上报真实执行轨迹──→ 行内 Trace Server
     │                                  ↑
     └─每轮响应返回 Trace ID─→ 测评执行器查询
                                        ↓
                              校验归属和证据完整性
                                        ↓
                             轨迹展示、JSON、过程评估
```

两条链路都必须成立：智能体负责产生和上报真实轨迹，AgentGate 负责查询并使用证据。配置查询地址不会自动让未上报的智能体具备上报能力。

当前工程已实现：

- ChatABC 基础编排、工作流和云虾执行过程中的 Trace 引用读取及每轮取证。
- 查询 Trace 详情和 LLM 请求附件，转换为统一测评证据。
- 校验项目、Trace ID、会话、被测 Pod 名称、输入、最终输出及 Span 数量与父子关系。
- 保留远端实际提供的模型、工具、检索等执行步骤及附件，供轨迹页面和过程评估使用。
- 对缺失、错配或不完整证据明确报错；不回退为仅凭最终回答完成取证。
- 取证失败不重放业务对话，Pod 按既有生命周期清理。

展示粒度取决于上游实际记录的数据。未记录的 Skill 或工作流内部步骤，不能由静态图谱推导成真实执行证据。取证发生在每轮回答结束后，不是运行中的实时 Span 流。

## 3. 行内需要准备什么

| 准备项 | 具体要求 | 建议负责方 | 完成凭据 |
|---|---|---|---|
| 服务地址与项目 | 提供查询地址和真实 `project_id`；地址只包含协议、主机和可选端口 | Trace 平台 | 地址、项目标识及接口说明 |
| 查询认证 | 当前支持独立 Bearer Token；凭据具备该项目查询权限 | Trace 平台 | 鉴权方式及权限确认；凭据通过部署渠道注入 |
| 执行节点网络 | 从实际 Celery Worker／BJS Job 验证 DNS、端口、TLS 证书信任、代理和访问策略 | 部署运维 | 执行节点成功查询一条指定 Trace |
| 智能体上报 | 被测智能体已上报真实执行步骤及需要分析的模型、工具数据 | 智能体平台 | 与真实调用对应的 Trace 及附件样例 |
| 对话关联 | 每轮返回唯一 SSE `trace` 引用；各轮源 Trace ID 不重复 | 智能体平台 | 完整 SSE 响应样例 |
| 查询协议 | 两条查询接口的路径、结构及字段语义符合当前契约 | 双方联调 | 详情和附件 JSON 对照结果 |
| 数据可见时序 | 每轮回答结束、开始查询时，证据已完整可查询 | 智能体平台、Trace 平台 | 连续多轮调用无暂时缺失或半成品证据 |
| 验收资源 | 有效行内登录、真实智能体版本、必要分支及一个两轮样本 | 测评负责人 | 可执行的测试任务及结果记录 |

浏览器或 API 服务能够访问 Trace Server，并不能证明实际执行任务的节点能够访问。

## 4. 最小配置及配置落点

在已有行内网关、数据库、登录认证和执行器配置基础上，设置：

```dotenv
AGENTGATE_AGENT_PLATFORM_MODE=inbank
AGENTGATE_TRACE_SERVER_URL=https://your-trace-host
AGENTGATE_INBANK_TRACE_PROJECT_ID=your-project-id
AGENTGATE_TRACE_SERVER_TOKEN=your-trace-query-token
```

上述值均为占位示例。URL 和项目 ID 为行内取证必需配置；仅在服务无需认证时，才可不设置查询 Token。

- **URL 限制**：只接受 HTTP(S) origin，不接受路径前缀、账号密码、查询参数或片段。
- **Token 分工**：行内登录使用真实会话 Token；Trace 查询使用独立服务凭据，两者不能互相替代。
- **Celery**：配置必须进入实际 Worker 环境，修改后重启相应执行进程。
- **BJS**：远端 Job 必须单独注入配置，并连接同一任务数据库、具备其他执行依赖。提交接口只传任务标识，不会自动转发行内 API 服务的环境变量或查询凭据；直接运行 `scripts/bjs/run_evaluation.py` 也不会自行加载 `.env`。
- **行内／行外隔离**：行内沿用真实目录和会话认证；行外沿用本地目录与 `local` Token，不读取行内 Trace 项目 ID。页面切换登录模式不能代替执行节点的 Trace 配置。

## 5. 必须对齐的协议

### 5.1 每轮 SSE Trace 引用

每轮必须包含且仅包含一个 Trace 引用。以下为事件内容示意，具体 SSE 包装沿用对应平台协议：

```text
event: trace
data: {"project_id":"your-project-id","trace_id":"source-trace-id","session_id":"actual-session-id","request_id":"actual-request-id"}

```

- `project_id` 和 `trace_id` 必填；项目必须与配置一致。
- 项目及 Trace 标识最多 128 字符，允许字母、数字、点、下划线和连字符，首字符为字母或数字。
- 引用中的 `session_id`、`request_id` 可选；若提供，必须匹配实际调用。
- 有 `done` 终止事件时，引用必须在其之前发送；云虾允许没有 `done`，但仍需在完整响应中提供唯一 Trace 引用。
- 对应证据必须在测评执行器开始取证时完整可查询；不同轮次使用不同源 Trace ID。
- SSE 中的 URL 不参与寻址，查询只使用执行环境中配置的 Trace Server 地址。

### 5.2 查询接口

当前客户端固定调用：

```http
GET /api/v1/projects/{project_id}/traces/{trace_id}
GET /api/v1/projects/{project_id}/traces/{trace_id}/llm_requests
```

| 响应 | 主要要求 |
|---|---|
| Trace 详情 | 包含 `trace`、`spans`、`observations`，沿用当前 camelCase 字段契约 |
| 根 Trace | 项目、Trace ID、`sessionId`、`agentName`、输入和输出匹配当前调用；`agentName` 对应本次创建的 Pod 名称 |
| 完整性 | 根状态为 `success`，`spanCount` 与完整 Span 数量一致；Span 时间、状态及父子关系有效 |
| LLM 附件 | 返回 `items` 数组；实际提供的附件保留到证据中，是否有足够内容用于分析需在联调中确认 |

接口路径相同不代表兼容，必须同时对齐字段结构和业务含义。以当前查询客户端和证据校验实现为准。

## 6. 当前限制与可能需要的适配

| 行内实际情况 | 当前限制 | 下一步动作 |
|---|---|---|
| 要求签名、自定义认证头、SSO 跳转或 mTLS | 当前没有相应的现成配置适配，查询使用独立 Bearer Token，且不跟随重定向 | 明确协议，由平台提供代理或评估代码适配 |
| 服务部署在 URL 路径前缀下 | 当前只接受 origin，并拼接固定接口路径 | 调整代理路由或适配查询客户端 |
| 回答完成后异步入库 | 当前没有等待入库的查询轮询机制，可能出现回答成功但取证失败 | 上游保证可查询时序，或设计有界等待机制 |
| JSON 字段或身份语义不同 | 严格校验可能拒绝证据，例如 `agentName` 并非本次 Pod 名称 | 先获取真实样例，再确定字段映射与协议调整 |
| 智能体未上报或未返回 Trace ID | AgentGate 无法建立本次调用与内部轨迹的关联 | 先补齐上游埋点、上报和引用返回 |
| 希望直接复用本工程的 HTTP 上报方式 | 本地桥接采用新增的 `agentgate.trace-bundle.v1`，不能假设行内已有服务支持 | 确认行内原生采集协议，或评估部署对应桥接入口 |

以上是接入条件和当前边界，不表示已经确认真实行内平台存在这些差异。

## 7. 建议联调顺序与完成标准

### 第一步：先获取一组真实样例

建议由平台方提供同一轮真实调用对应的：

1. 完整 SSE 响应。
2. Trace 详情 JSON。
3. LLM 请求附件 JSON。
4. 查询地址、项目标识、鉴权方式和入库时序说明。

样例可脱敏，但应保留字段结构和各标识之间的一致关系；真实查询凭据通过部署渠道注入，不写入样例或文档。

**完成标准**：确认是否能直接按现有契约接入；若不能，明确具体差异及责任方。

### 第二步：从实际执行节点验证查询

在实际 Worker／BJS Job 环境配置服务地址、项目及认证，查询一条已存在的真实 Trace，验证两条接口和字段解析。

**完成标准**：网络、TLS、鉴权、项目权限和响应契约均通过。

### 第三步：执行真实两轮测评

选择真实智能体和版本；云虾选择必要分支。使用输入不同的两轮样本，串行执行、重试次数为 0，先使用最终输出评估器跑通完整链路。

**完成标准**：

- 每轮能关联到不同的真实源 Trace，输入输出及会话与本次调用一致。
- 样本详情展示上游实际提供的模型、工具等内部步骤，节点与 JSON 能对应。
- 证据包含 `inbank.evidence_mode=trace_server`、实际 `trace_sdk.trace_id` 和 `trace_sdk.replay=false`。
- 根据真实返回的工具和路径配置过程规则，能够解释命中结果。

### 第四步：验证失败处理

在测试环境使一条 Trace 引用失效或让查询被拒绝，观察任务状态和调用次数。

**完成标准**：明确报错、不重复执行业务对话，Pod 得到清理；只有回答而没有内部证据不算验收通过。

## 8. 下一步决策

| 联调判断 | 推荐动作 |
|---|---|
| 已上报、引用完整、查询与鉴权协议匹配 | 进入配置联调与真实验收，暂无证据表明需要新增适配 |
| 已有真实证据，但接口、字段、鉴权或入库时序不同 | 明确差异后开展对应适配，再做验收 |
| 未上报或未返回 Trace 引用 | 先由智能体平台补齐上游链路，再进入测评取证联调 |

当前最有价值的下一步是取得“一轮真实调用的完整样例”，据此决定是直接联调还是补充适配。

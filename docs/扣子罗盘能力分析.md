# 扣子罗盘能力分析

调研日期：2026-10-08  
对照工程：AgentGate，`integration/baibo`，提交 `4f80e22`  
调研入口：[扣子罗盘评测集](https://loop.coze.cn/console/enterprise/personal/space/7694189601988444210/evaluation/datasets)

## 一、结论

扣子罗盘在通用评测的易用性、数据配置和结果反馈闭环上更完整。AgentGate 的优势集中在银行智能体接入，以及工具、工作流、Skill 和业务状态的明确检查。

当前最值得补齐的是评估器独立调试、参考答案输入、人工校准持久化。相比先扩充评估器模板数量，优先让用户能够自行创建、调试、发布并验证裁判，更能提高工程的实际可用性。

## 二、调研范围与证据边界

本次使用用户已经登录的 Safari，实际查看了以下页面：

- 评测集列表与新建评测集页面。
- 自建／预置评估器目录及筛选项。
- “Agent 轨迹质量”评估器定义与“预览与调试”面板。
- 实验列表与新建实验流程。

调研时，该空间没有现成评测集、自建评估器和实验。因此，实验结果报告、人工校准、在线评测、智能优化等能力依据官方文档，未在该账号运行验证。本次没有创建实验或消耗评测额度。

AgentGate 对照依据为上述提交的源码、此前回归记录，以及三个贷款智能体的规则、LLM、混合评估共九项真实模型冒烟验收。冒烟验收说明这些执行链路可以工作，不代表所有产品入口均已完善，也不代表真实行内联调已经通过。

本文中的“未见”表示本次页面或代码检查未确认该能力，不能据此断言产品完全不具备该能力。页面数量、模型限制和邀测资格均为调研时状态。

## 三、能力差异对照

| 能力 | 扣子罗盘 | AgentGate 当前状态 | 差异判断 |
|---|---|---|---|
| 评测集结构 | 页面提供理想输出、工作流、轨迹三种预设；支持自定义列、类型和必填项 | 使用固定的样本／轮次结构，输入可放 JSON，期望支持输出、工具、状态、执行路径等 | 罗盘适合通用数据配置；AgentGate 更适合表达明确的业务验收条件 |
| 导入与版本管理 | 本地导入、列映射、类型校验、版本提交；支持多模态数据 [1] | 已有 JSON、Excel、CSV、ZIP 导入、预览和版本发布；主要依赖标准字段及约定格式 | 基础能力已具备，缺少同等灵活的字段映射和数据类型编辑体验 |
| 预置评估器 | 页面实际显示 68 项；按类型、对象、目标、业务场景筛选，包含任务完成、轨迹、CUA、图片等 | 已有规则／LLM／混合目录及贷款专项评估器，覆盖重点更集中 | 罗盘覆盖面更广；数量本身不代表对贷款业务判断更准确 |
| 评估器自定义 | LLM Prompt、变量、模型配置；Code 支持 Python、JavaScript [2] | 可配置 LLM 评分标准、发布版本、组合规则；规则依赖后端已有实现，不支持用户任意编写代码 | 罗盘扩展更方便；AgentGate 的业务规则更受控 |
| 评估器独立调试 | 页面有独立“预览与调试”；官方说明可构造输入并试运行 [2] | 有真实任务执行和模型调用记录，但缺少完整的独立试评分入口；另有明确标注的 Mock 演示 | 明显缺口：修改裁判后验证成本偏高 |
| 参考答案与字段映射 | 将评测集字段、实际输出映射到评估器变量 [3] | LLM 输入目前仅选择最终回答、回答＋工具、完整轨迹；未把样本期望输出自动传给 LLM | 关键缺口：参考答案无法自然参与 LLM 判分 |
| 规则＋LLM 组合 | 实验可配置多个评估器 [3]；本次未确认与 AgentGate 等价的显式混合判定模型 | 有显式混合评估器，支持全部通过、任一通过、加权得分及阻断检查 | AgentGate 已有明确的组合判定能力，值得保留 |
| 实验与对比 | 支持多个实验选择基准、指标比较、逐样本输出／评分／Token／时延比较 [3] | 已有单任务、A/B、稳定性、版本快照及样本差异；对比主要是两组兼容配置 | 罗盘的多实验分析更完整；AgentGate 更强调严格控制配置一致性 |
| 轨迹评估 | 页面提供轨迹质量评估器；官方支持轨迹字段映射、回流后评测，具体依赖支持的接入方式 [4] | 已有 Trace 图＋JSON 联动，LLM 可读取完整轨迹，规则可检查工具参数、顺序和工作流路径 | 两者都有能力；AgentGate 在明确执行约束上有可保留的特色 |
| 人工校准 | 支持修正分数与原因，并联动实验统计 [3] | 已有逐轮／工具标注、期望修正、回写测评集草稿；标注主要存浏览器，未形成完整的服务端裁判校准流程 | 明显缺口：团队共享、审计和校准评估器还不完整 |
| 线上数据闭环 | 从 Trace 按条件采样，自动评测或回流测评集 [5] | 已有 Trace 采集、查询、底层回放能力和人工回写；未见面向用户的完整在线采样评测流程 | 定时执行已有测评集，不等于线上 Trace 自动评测 |
| 评测驱动优化 | 官方提供基于 Bad Case／优质样本优化 Prompt，但注明需要定向邀测资格 [6] | 已有问题分析、改进建议、回归测评集和 A/B 验证；尚未自动生成并验证候选 Prompt | 当前主要依靠人工执行改进，不能称为自动优化闭环 |

## 四、AgentGate 最需要补齐的四个问题

### 4.1 LLM 裁判没有自然使用参考答案

当前送给裁判的是用户输入、实际输出及可选工具记录／轨迹。人工修正期望后，可以影响相关规则检查，但不会自动让 LLM 按新答案判分。

这会削弱“人工标注改进评估器”的效果。对需要业务标准答案的场景，裁判应明确获得参考答案及其来源，同时将它与实际执行证据区分开。

源码依据：

- [Judge 输入构造](../src/agentgate/evaluator/judge/prompt.py)：`select_material` 当前构造 `turn_inputs`、`final_output`，并按范围附加工具、轨迹和最终状态。
- [评估器编辑器](../frontend/src/views/evaluation/components/EvaluatorEditor.vue)：页面明确说明不支持任意字段映射，也未将样本期望输出传给 LLM。

### 4.2 “评分模板”与真实评估器仍然脱节

“评分模板”页面的新建／复制只生成前端 UX 草稿，刷新即清除，也不会修改后端裁判。真实评估器已有后端版本管理，但两个入口的完成度不同，容易让使用者误以为修改已经生效。

应将评分模板与可执行评估器的关系明确化：保存在哪里、是否已发布、哪些任务引用了哪个版本，都需要在页面上可验证。

源码依据：[评分模板页面](../frontend/src/views/evaluation/components/ScoringTemplates.vue)。页面明确提示“新建与复制为 UX 草稿，刷新后清除；不会修改后端裁判”。

### 4.3 人工标注尚不是可靠的团队资产

当前会话标注记录写入 `localStorage`。回写后的测评集可以保存到后端，但原始人工评分、意见和模板仍主要依赖当前浏览器。

因此，“人工标注可以回写测评集”与“人工标注本身已支持团队共享、审计和跨设备使用”是不同的完成状态。

源码依据：

- [人工标注存储](../frontend/src/stores/modules/review.ts)：`readAnnotations`、`saveAnnotationTask` 使用浏览器本地存储。
- [V2 标注回写](../frontend/src/views/evaluation/components/AnnotationV2Feedback.vue)：通过后端接口创建或更新测评集草稿。

### 4.4 模型可真实调用，但模型选择体验没有完整接通

已配置的 DeepSeek 评估器确实跑过真实任务，保留了模型、分数和调用记录。然而评估器编辑页的模型目录仍返回空列表，依赖复制已有配置或导入管理员配置。

应将“已有配置能够运行”与“用户能够自行选择模型并测试连接”分别验收，不能以运行成功代替整个配置流程完成。

源码依据：[评估器编辑器](../frontend/src/views/evaluation/components/EvaluatorEditor.vue)中的 `loadModels`。另外的[模型引用组件](../frontend/src/views/evaluation/components/EvaluatorModelSelect.vue)能够展示默认连接状态和编辑模型引用，但这不等于统一模型目录和真实连接测试已经完成。

## 五、应保留的工程特色及其边界

### 5.1 面向执行过程和业务结果的明确约束

贷款智能体不能只检查回答是否看起来正确。AgentGate 已有以下检查能力：

- 必需工具与禁止工具。
- 工具参数、调用出现位置及匹配条件。
- 最终业务状态与输出条件。
- 工作流执行路径和顺序。
- Skill 路由及允许工具约束。
- 规则与 LLM 组合，以及阻断性检查。

这些能力能够把业务验收标准表达成可重复执行的条件。相关实现见 [规则评估器](../src/agentgate/evaluator/rule/)、[执行路径检查](../src/agentgate/evaluator/rule/execution.py)、[混合评估器](../src/agentgate/evaluator/hybrid.py)。

### 5.2 行内／行外隔离和证据关联

工程区分行内真实目录、会话令牌与行外本地目录、模拟令牌，并固定测评任务中的智能体版本／分支。新实现的行内取证通过配置的 Trace 服务查询证据，验证其与本次会话、Pod、输入输出及轮次的关联。

真实行内网关与客户 SDK 部署尚未联调，因此这里属于已实现并完成接口契约验证的能力，不能表述为真实行内生产验收通过。详见[行内取证验收说明](inbank-evidence-acceptance.md)。

### 5.3 Skill 静态分析的实际范围

现有静态分析主要检查 Skill 职责描述的重叠、冲突、重复与路由歧义，不是全面代码审计，也不代表实际调用准确率。

行内 Skill 静态分析仍因缺少真实版本定义接口而暂缓。扣子罗盘本次查看范围内未见对应的专门 Skill 静态分析入口，不能据此断言其完全不具备相关能力。

相关实现见 [Skill 分析工作流](../src/agentgate/application/skill_analysis.py)、[静态分析页面及范围说明](../frontend/src/views/evaluation/components/UpstreamAnalysis.vue)。

## 六、改进优先级建议

以下为产品改进建议，不代表已经实现或已启动实施。

| 优先级 | 建议 | 用户可获得的结果 | 建议验收标准 |
|---|---|---|---|
| P0 | 打通真实模型选择、评分模板保存发布、评估器独立调试 | 创建裁判后，当场用样本看到真实分数、理由和调用记录 | 刷新后配置仍在；指定版本可被任务引用；调试失败明确展示错误 |
| P0 | 区分输入、实际输出、参考答案、轨迹，并提供字段映射 | 人工修正的期望能成为 LLM 的评判依据 | 调试页面能预览实际传给裁判的材料；缺少必需字段时阻止执行 |
| P0 | 人工标注入库，分别保留机器分、人工分、修正原因和版本 | 换电脑可继续，团队可复核，原始机器结果可追溯 | 不覆盖原始自动结果；可查询修改人、时间、依据和修订记录 |
| P1 | 建立裁判校准集，对比新旧评估器的人机一致率和误判率 | 判断裁判是否变准，而不只是分数被人工改过 | 固定证据和人工标准，分别运行新旧裁判，展示分歧样本和错误类型 |
| P1 | 固定历史输出／Trace，只重评裁判；扩展多实验对比 | 避免 Agent 重跑引入波动，更准确地比较评估器 | 重评不调用被测 Agent；保留证据指纹与评估器版本 |
| P2 | 增加线上 Trace 采样回流，再逐步扩展多模态和 Code 评估器 | 持续从实际问题补充回归用例 | 采样来源、条件和结果可追溯；新增执行能力有明确边界和失败处理 |

## 七、人工标注如何驱动裁判和 Agent 改进

人工改分不等于评估器已经改进，评估器变准也不等于 Agent 已经改进。应分别验证两条链路。

### 7.1 验证裁判是否变准

1. 固定一批样本及其实际输出、工具记录、Trace，不重新运行 Agent。
2. 由人工给出标准评分、错误类型和判断依据，保留修订记录。
3. 调整裁判 Prompt、评分标准、输入材料或模型，发布新评估器版本。
4. 对同一份证据分别运行新旧裁判。
5. 比较人机一致率、误判率和重点错误类型，检查原有正确判断是否退化。

建议保留独立验收样本，避免仅在参与修改评分标准的样本上验证效果。

### 7.2 验证 Agent 是否变好

1. 固定测评集及经过验证的裁判版本。
2. 将问题归因到 Prompt、工具参数、工作流节点、Skill 路由或业务规则。
3. 修改 Agent 对应部分，保留候选版本。
4. 通过回归和 A/B 对比新旧 Agent。
5. 同时检查目标问题改善、阻断项、其他场景退化及执行成本。

这两条链路分别回答“评分是否可信”和“被测对象是否改善”，需要分别保留证据与版本。
